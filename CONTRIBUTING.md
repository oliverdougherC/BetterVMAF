# Contributing

BetterVMAF is a small native macOS application. Prefer focused changes that make video comparisons more trustworthy or easier to understand.

## Local build

Use macOS 15.2+ with a compatible Xcode 16+ installation. CI selects Xcode 16.4 on its macOS runner; keep the shared scheme usable without a contributor's personal signing team.

```bash
xcodebuild -project VMAF.xcodeproj -scheme VMAF -configuration Release -destination 'platform=macOS' CODE_SIGNING_ALLOWED=NO build
```

Run tests using local ad-hoc signing (no paid developer account is needed):

```bash
xcodebuild -project VMAF.xcodeproj -scheme VMAF -configuration Debug -destination 'platform=macOS' CODE_SIGN_IDENTITY=- CODE_SIGN_STYLE=Manual DEVELOPMENT_TEAM= test
```

Current tests primarily exercise building and launching. They do not establish metric correctness, cancellation safety, or timing/color fidelity. Those need the regression fixtures listed in Linear. Linux source inspection cannot substitute for running the Mac app.

## Make a change

1. Start from current `main` and create a short-lived task branch.
2. Link the relevant Linear issue in the pull request. Keep public GitHub bug reports linked to that issue.
3. Implement the smallest coherent change. Include regression coverage for bugs with meaningful observable outcomes.
4. Run the relevant build/tests and inspect UI changes on macOS. For metric changes, compare against the pinned command-line engine using the same preprocessing and fixtures.
5. Report what passed and what could not be exercised. Merge after review and checks, then remove the task branch.

Avoid committing Xcode user state, derived data, reports generated by test runs, or downloaded media. Small deterministic fixtures and their provenance belong in source control; large corpora should use a versioned manifest and separate downloads.

## Package a local build

```bash
./create_dmg.sh
```

The script runs from the repository location, uses temporary staging, and writes `Better-VMAF.dmg`. This is a local unsigned package, not a notarized release. Validate helper architecture, bundled resources, executable permissions, and clean-machine startup before distributing a new release. Track release signing/notarization separately from local build success.

## Metric changes

Read `docs/QUALITY_STRATEGY.md` first. A metric must retain its name, version, direction, units, coverage, and input normalization. An unsupported metric is unavailable, not zero. Cross-version or cross-profile results must not be silently ranked together.

Do not claim a new metric improves subjective agreement without evidence. Do not change thresholds just to make fixtures pass. Keep size/bitrate savings separate from quality and distinguish full analysis from sampling.
